# Chatbot Tracing - Failure Patterns & Analysis Guide

This guide is dedicated to analyzing traces generated by the **chatbot** (evals) package. Traces are located in `tests/evals/traces/chatbot/<datetime>_<runId-short>/`.

## Inspector Commands

Start here:

```bash
npx tsx .agents/skills/trace-analyzer/references/inspect-evals.ts summary
npx tsx .agents/skills/trace-analyzer/references/inspect-evals.ts compact
npx tsx .agents/skills/trace-analyzer/references/inspect-evals.ts judge
npx tsx .agents/skills/trace-analyzer/references/inspect-evals.ts model-conversation <runId>
```

---

## 1. Analysis Workflow

Follow this progressive disclosure flow:

### Phase 1: Run Triage (Always Start Here)
1. **Read `summary.json`**:
   - Check `"status"`. If it's `"error"`, the model or pipeline failed.
   - Inspect `"tokens"`. Look at the input vs output token consumption.
   - Look at the phase counts in `"counts.byPhase"`.
   
2. **Check `errors.ndjson`**:
   - If `"status"` is `"error"`, open `errors.ndjson`.
   - Look at the `phase` and `payload` of the error events. This helps identify network timeouts, API rate limits, or context window limits.

### Phase 2: Compaction & Fact Recall (If Triage is Insufficient)
1. **Open `lifecycle.ndjson`**:
   - Look at the `start` and `finish` events.
   - Locate the compaction event: look for an event with `phase: "finish"` or metadata where compaction was triggered.
   - Check `tool-call` and `tool-result` phases. Did the chatbot use the correct tools after compaction?
   - Look at `source` phases. Did it retrieve the correct RAG documents?

### Phase 3: Deep Stream Debug (Only for generation quality/streaming details)
1. **Open `stream.ndjson`**:
   - Merge `lifecycle.ndjson` and `stream.ndjson` using `inspect-evals.ts model-conversation <runId>` to reconstruct the exact text and reasoning blocks step-by-step.
   - Analyze the model's inner thoughts in `reasoning-delta` (what the model was thinking before making tool calls or responding).
   - Verify if the chatbot mentioned the injected facts before compaction, and if it recalled them after compaction.

## 2. Common Chatbot & Compaction Failures

### Pattern: Facts Lost After Compaction
* **Symptoms**: Compaction Occurred = 1.0, but Fact Recall < 0.5.
* **Analysis**: Reconstruct the conversation. Check the compaction summary text in `lifecycle.ndjson` (under metadata).
* **Causes**:
  - The summary model did not include the personal facts (Zephyr, NebulaForge, Quarkle) in the context summary.
  - The facts were mentioned too early and were completely omitted from the context window during compression.
* **Resolution**: Adjust the compaction prompt to emphasize preserving personal context and user facts, or check if the summary model needs to be upgraded.

### Pattern: Compaction Never Triggered
* **Symptoms**: Compaction Occurred = 0, Fact Recall = 0.
* **Analysis**: Check `summary.json` `"counts.byPhase"`. Are there any compaction triggers?
* **Causes**:
  - The conversation did not reach the threshold size.
  - The `DEFAULT_CONTEXT_WINDOW` environment variable is set too large (the default is 128k; for tests it must be constrained, e.g. 16k).
* **Resolution**: Set `DEFAULT_CONTEXT_WINDOW=16000` in the environment before running evals.

### Pattern: Low Compression Ratio
* **Symptoms**: Compaction Occurred < 1.0 (compression ratio < 10x).
* **Analysis**: Look at the size of the summary vs the original conversation.
* **Causes**:
  - The compaction summary was too wordy/verbose.
* **Resolution**: Constrain the summary length in the compaction system instructions.

### Pattern: Tool Usage Failures
* **Symptoms**: Tool call count is 0, or tools return errors.
* **Analysis**: Check `lifecycle.ndjson` for `tool-call` and `tool-result`.
* **Causes**:
  - `NEXT_PUBLIC_ENV` is set to `"test"` instead of `"evals"`, activating mocks and deactivating tools.
* **Resolution**: Verify environment variables and ensure the runner forces `NEXT_PUBLIC_ENV=evals`.
