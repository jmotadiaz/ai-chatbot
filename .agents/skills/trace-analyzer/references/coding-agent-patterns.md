# Coding Agent Tracing - Failure Patterns & Analysis Guide

This guide is dedicated to analyzing traces generated by the **coding-agent** package. Traces are located in `packages/tracing/traces/coding-agent/<datetime>_<runId-short>/`.

---

## 1. Analysis Workflow

Follow this progressive disclosure flow:

### Phase 1: Run Triage (Always Start Here)
1. **Read `summary.json`**:
   - Check `"status"`. If it is `"error"`, there is a guaranteed failure.
   - Inspect `"counts.byLevel"`. Are there `"error"` or `"warn"` events?
   - Check total duration `"durationMs"`. If it's unusually high (>30,000ms), suspect a timeout or hang.
   
2. **Check `errors.ndjson`**:
   - If `"status"` is `"error"`, open `errors.ndjson`.
   - Look at the `eventName` and `payload` of the error events. This usually gives the root cause immediately (e.g., failed RPC call, session creation error, database exception).

### Phase 2: Lifecycle & Timing (If Triage is Insufficient)
1. **Open `lifecycle.ndjson`**:
   - Look at the sequence of RPC calls (`rpc.request` -> `rpc.response`).
   - Identify which step or call took the longest by checking `durationMs` on `_end` events (e.g., `worker.sendPrompt_end`, `worker.initialize_end`).
   - Check if there is a gap in timestamps between successive events.

### Phase 3: Deep Stream Debug (Only for streaming issues)
1. **Open `stream.ndjson`**:
   - Inspect streaming deltas and translate events (`translate`, `stream.event`, `pi.event`).
   - Look for malformed stream items or translation mismatches (`translate.unknown_type`).

## 2. Common Coding Agent Failures

### Pattern: Session Not Found
* **Symptoms**: RPC calls fail, `summary.json` has error status, or bridge logs show lookup failures.
* **Error check**: Check `errors.ndjson` for `db.lookup` containing `found: false` or `Session not found`.
* **Resolution**: Verify if the session ID passed to the request is initialized or if it has expired/deleted in the database.

### Pattern: Worker Unreachable / HTTP Error
* **Symptoms**: Long execution duration followed by a crash.
* **Error check**: Check `errors.ndjson` for `rpc.http_error` or connection refused/timeout events.
* **Resolution**: Verify if the background worker process is running and accessible at the configured URL.

### Pattern: Pi SDK Crash / Prompt Error
* **Symptoms**: Run fails during model output generation.
* **Error check**: Check `errors.ndjson` or `lifecycle.ndjson` for `session.prompt_error`.
* **Resolution**: Examine the `payload` to see the underlying error returned by the AI provider (e.g., context length exceeded, invalid API key, safety filter triggered).

### Pattern: Malformed Stream Event
* **Symptoms**: UI displays raw or incomplete text blocks.
* **Error check**: Check `stream.ndjson` or `errors.ndjson` for `translate.unknown_type` or stream parsing warnings.
* **Resolution**: Review the translator logic in `pi-to-agui-translator.ts` to support the new event type emitted by the SDK.
